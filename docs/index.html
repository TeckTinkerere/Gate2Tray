What it is

An operating layer for a one-person aviation-commerce company.

Gate2Tray is not an airline, caterer, or payment processor. The airline stays the operator of record and the merchant; licensed caterers stay responsible for food and loading; cabin crew keep final authority over service and safety. Gate2Tray orchestrates inventory already loaded onto partner flights — pricing opportunities, passenger ordering, crew fulfillment, exceptions, refunds, and reconciliation — so one operator can run a portfolio that would otherwise need a whole retail-operations team.

Recover margin, safely

Recommend policy-bounded gate offers on likely-surplus meals — never discounting into protected stock or below the minimum contribution margin.

Many flights, one queue

Turn several simultaneous flights into a single prioritized attention queue: pending approvals, inventory risk, active exceptions, and the agent trail — in that order.

Exceptions with consent

Resolve stockouts through verified, fully dietary-compatible substitutes the passenger explicitly chooses — otherwise a visible, idempotent refund path.

The operating sequence

Observe. Recommend. Approve. Execute. Log.

The whole product is legible as one repeating loop. Nothing consequential happens without evidence behind it and a human accountable for it.

01

Observe

Read a versioned flight snapshot: manifest, menu, inventory, orders, exceptions, freshness.

02

Recommend

Deterministic demand evaluation and a policy-checked offer — or an honest no-action / needs-data result.

03

Approve

Consequential actions suspend for the right human: operator, crew, or an explicit passenger choice.

04

Execute

Run once against an expected state version with an idempotency key. Stale state is rejected.

05

Log

Append immutable events linking evidence, policy, approval, tool call, and outcome.

Four surfaces, one database

Each screen optimized for its context.

Accountable control for the operator, arm's-length glanceability for crew, and reassurance for passengers — all responsive from 320px to 1440px and connected through one local SQLite state.

/operator

Command center

A fleet attention queue, then a per-flight workspace: evidence → recommendation → policy → approval → outcome → linked audit. Policy edits are versioned, never hidden constants.

/crew/[flight]

Cabin surface

Only the selected flight: service controls, section queues, inventory, exceptions. Start or pause service, mark an item unavailable, confirm delivery — in one or two taps.

/order/[flight]

Passenger ordering

A flight-specific menu, simulated checkout, reservation status, and a tracking link — focused, mobile-first, and reassuring.

/track/[orderId]

Resolution tracker

Live order status with explicit compatible substitute choices and an always-visible refund fallback, holding stable through terminal states.

The bounded agent

One CommerceOpsAgent — not a theatrical swarm.

Authoritative arithmetic, policy checks, state transitions, payments, inventory, and safety rules stay deterministic. An optional LLM may later choose among safe read/propose tools and explain a recommendation — but it can never calculate authoritative prices, issue arbitrary writes, touch SQL, pick a passenger's meal, or bypass a human gate.

What the agent guarantees

  • ✓Recommendation values change when the structured inputs change — no fabricated precision.
  • ✓Insufficient evidence returns an honest needs-data state instead of a guess.
  • ✓An approval signs the exact action digest, expires, and is superseded if state or policy moves.
  • ✓Approved writes execute exactly once; retries can't oversell or duplicate a refund.
  • ✓Every query and command carries a flightId — a command for flight A can't touch flight B.
  • ✓Typed, actionable errors: STALE_VERSION, POLICY_DENIED, APPROVAL_REQUIRED, INVENTORY_CONFLICT…

System architecture

Role-scoped commands through a policy kernel.

The agent control plane owns no commerce records. It writes only through domain services, behind approval and consent gates, into SQLite state and an append-only event log.

   Operator / Crew / Passenger / Tracker UI
                    |
             role-scoped commands
                    |
  Flight | Inventory | Commerce | Fulfillment
                    |
       Policy kernel + approval/consent gates
              |                 |
         SQLite state    append-only events
              ^                 |
              +---- agent executor ----+
                         |
                CommerceOpsAgent
  • ▸Flight Operations — lifecycle, manifest snapshot, gate, aircraft-change and service state.
  • ▸Inventory — loaded, reserved, unavailable, and protected units, with optimistic concurrency.
  • ▸Commerce — flight menu, price snapshots, orders, simulated payments and refunds.
  • ▸Fulfillment — cabin queues, delivery, unavailable-item exceptions, passenger choices.
  • ▸Policy & Approval — immutable policy versions, deterministic decisions, expiring approvals, action digests.
  • ▸Agent control plane — runs, tool calls, forecasts, recommendations, and audit links.

Run it locally

# clone and install
git clone https://github.com/TeckTinkerere/Gate2Tray.git
cd Gate2Tray
npm install

# quality gates
npm run lint
npm test
npm run typecheck
npm run build

# start the demo
npm run dev
# → open http://localhost:3000/operator

To scan the QR from a phone, run npm run dev -- --hostname 0.0.0.0 and open the operator page via your computer's LAN address.

Try the walkthrough

  • 1Run the operations agent on /operator.
  • 2Approve the recommended gate discount and scan the flight QR.
  • 3Place a meal order on /order/MC201.
  • 4Start service on /crew/MC201, mark a meal unavailable, open the passenger choice.
  • 5Approve a substitute or complete the simulated refund on /track/[orderId].
  • 6Switch across the five flights to see different bounded outcomes and scoped audit trails.

⚠︎ This is a demo, and it says so honestly

No identity authentication, no role authorization at the network edge, and no real payments. Commercial targets and conversion inputs are labelled hypotheses or scenario fixtures — not validated results. Run it only with mock data on a trusted local network; it is not a production airline or payment system.
